# 双栏骨架规范（Web / 移动端共用）

这份文档定义「左原型 · 右说明」单文件引擎的硬契约。模板里已经实现好全部交互，
你只需要往里面填内容。**标了「勿改」的部分改了就会让联动失效。**

---

## 1. 文件契约

引擎靠下面这些锚点工作，生成时不得重命名：

| 锚点 | 作用 | 能否改 |
|---|---|---|
| `<html data-platform="web\|mobile">` | 平台标识，脚本据此写文件名和校验策略 | **勿改** |
| `#topbar` / `#tb-sys` / `#tb-tag` | 顶栏、系统名、平台标签 | 可改文案 |
| `#proto` | 左侧原型区 | 往里加内容 |
| `#prd` / `#prd-body` | 右侧说明区、说明渲染宿主 | **勿改结构** |
| `#prd-data` | 数据源 JSON 脚本块 | **只改内容，不改标签** |
| `.page[data-menu="<id>"]` | 一个菜单对应一块原型页面 | 可增删，`data-menu` 必须对得上 |
| `[data-menu-btn="<id>"]` | 原型里的导航项（侧边栏/tabbar） | 可增删 |
| `[data-fp="<n>"]` | 挂了功能点编号的元素 | 可增删 |
| `[data-fp-card="<n>"]` | 右侧说明卡片的挂载点（脚本自动生成） | 不用手写 |
| `#toggle-prd` / `#btn-hide` | 收起说明栏 | **勿改** |
| `#btn-edit` / `#btn-export` | 编辑态、导出 | **勿改** |

**关键约束**：`data-menu` 的值、`data-fp` 的数值，必须在 `PRD_DATA` 里有对应条目，
两边任何一侧多出来都会被 `validate.mjs` 判为错误。

## 2. PRD_DATA 结构

整个右侧说明由 `<script id="prd-data" type="application/json">` 里的 JSON 驱动。
改右边说明 = 改这段 JSON；不要去改渲染出来的 DOM。

```jsonc
{
  "system": "智宇CRM",              // 系统名，同时用于导出文件名
  "platform": "web",                 // web | mobile，必须与 html 的 data-platform 一致
  "theme": { "primary": "#2563EB" }, // 主色，会写入 CSS 变量
  "menus": [
    {
      "id": "lead",                  // 必须与 .page[data-menu] 一致
      "name": "线索管理",
      "summary": "一句话说明这个菜单干什么。",
      "sections": [ /* 见下 */ ]
    }
  ]
}
```

`__savedAt` 由编辑器自动写入，不要手填。

### 2.1 七种章节类型

| type | 用途 | 渲染形态 | 位置 |
|---|---|---|---|
| `layout` | **布局说明** | 键值列表（页面顶部 / 页面主体 / 空状态 / 底部 / 刷新机制） | **恒排最前** |
| `overview` | 页面概述 | 由 `blocks` 渲染成段落 / 键值表 / 列表 / 表格 | 中 |
| `interactions` | **交互说明** | 每个面板一张卡：面板名称 + 触发方式 / 面板内容 / 关闭方式 / 展现形式 / 动画效果 | 中 |
| `permission` | 权限说明 | 四列表：功能点🔒 / 操作权限 / 数据权限 / 备注 | 中 |
| `features` | 功能说明 | 每个功能点一张卡片，编号 + 名称🔒 + 描述 + 前置条件 + 业务流程 + 字段表 + 规则 + 状态 | 中 |
| `exceptions` | **异常场景** | 每条一张卡：场景 + 系统表现 + 提示文案 | **恒排最后** |
| `custom` | 自定义章节 | 同 overview，但带删除按钮，可整块删掉 | 中 |

`layout` 和 `exceptions` 的位置由引擎强制排序，不管在 JSON 里写在第几个，渲染时都会归位。

### 2.2 blocks 的四种块

```jsonc
{ "type": "para",  "text": "一段说明文字。" }
{ "type": "kv",    "rows": [{ "k": "页面路径", "v": "/lead/list" }] }
{ "type": "list",  "items": ["第一条", "第二条"] }
{ "type": "table", "head": ["列1","列2"], "rows": [["a","b"]] }
```

`kv` 的 `k` 是锁定列（不可在页面上改），`v` 可改。

### 2.3 features 里的功能点

```jsonc
{
  "fp": 1,                          // 功能点编号，整数，同一菜单内不可重复
  "name": "线索列表查询",            // 🔒 锁定，改了原型就对不上
  "desc": "按条件筛选线索，结果分页展示。",

  "precondition": "已登录且具备「线索-新增」权限；数据字典已配置来源选项",
                                    // 可选。没有前置条件就整条省略，不要留空字符串
  "flow": [                         // 可选。竖向时间线，4~8 个节点最合适
    { "t": "点击「+ 录入线索」",        "type": "start" },
    { "t": "弹出弹窗，聚焦「线索名称」", "type": "step" },
    { "t": "必填与格式校验",           "type": "branch", "note": "不通过 → 字段标红并聚合提示" },
    { "t": "名称查重",                "type": "branch", "note": "重复 → 阻止提交" },
    { "t": "保存成功，列表高亮新记录",   "type": "end" }
  ],

  "fields": {                       // 可选
    "table": "list",                // list | form-add | form-edit | detail
    "caption": "筛选与列表元素",
    "rows": [ { "el": "...", "type": "...", "logic": "...", "note": "..." } ]
  },
  "rules": ["业务规则一", "业务规则二"],   // 可选
  "exceptions": [                    // 可选。**只写这个功能点自己的异常**
    {
      "scene": "手机号已存在",
      "behavior": "不阻止提交，弹二次确认，可选「继续新增」或「合并到已有线索」",
      "message": "「该手机号已有线索，是否合并？」"
    }
  ],
  "states": ["待跟进", "跟进中", "已转化"] // 可选，渲染成 → 串联
}
```

**`exceptions` 分两级，别混：**

| 级别 | 写在哪 | 写什么 | 判断口径 |
|---|---|---|---|
| 功能点级 | `features.items[].exceptions` | 这个功能点自己的边界情况：校验不通过、状态冲突、重复提交、单个接口失败 | 换掉这个功能点，这些异常就不存在了 |
| 页面级 | 独立的 `exceptions` 章节 | 跨功能点的通用情况：断网、无权限、整页加载失败、强制更新、浏览器过低 | 换掉任何单个功能点，这些异常依然存在 |

**别把功能点级的往页面级塞。** 页面级没有编号，研发看到「支付超时」得自己猜它归倒计时还是归支付按钮——
放在功能点里，异常和 `fp` 编号天然绑定，谁做这个功能点就归谁。

**flow 节点的三种类型**

| type | 节点样式 | 用在哪 |
|---|---|---|
| `start` | 蓝色实心圆 | 流程起点，一条流程只有一个 |
| `step` | 蓝色描边圆 | 顺序执行的动作 |
| `branch` | 琥珀色圆角方块 | 判断点，必须配 `note` 写清各分支走向 |
| `end` | 绿色实心圆 | 流程终点 |

`note` 写成「条件 → 结果；条件 → 结果」的形式，一条 note 里不要超过 2 个分支，
超过就拆成两个节点。

### 2.4 layout 章节

```jsonc
{
  "type": "layout",
  "title": "布局说明",
  "rows": [
    { "k": "页面顶部", "v": "标题「核销端」+「扫码核销」大按钮（主色突出）+「手动输入」文字按钮" },
    { "k": "页面主体", "v": "待核销订单列表（每行：订单号、核销码大字、菜品摘要、金额、下单时间、等待时长），空状态展示「暂无待核销订单」" },
    { "k": "下方折叠区", "v": "「已核销」订单列表，默认收起，点击展开" },
    { "k": "刷新机制", "v": "列表支持 5 秒自动刷新" }
  ]
}
```

`k` 建议用固定词：**页面顶部 / 页面主体 / 空状态 / 底部 / 刷新机制 / 响应式**，
有需要再加「筛选区」「下方折叠区」「辅助区」。**每个菜单都必须有一条 layout。**

### 2.5 interactions 章节

```jsonc
{
  "type": "interactions",
  "title": "交互说明",
  "items": [
    {
      "panel": "取消订单确认弹窗",                    // 面板名称（必填）
      "trigger": "在「待付款」订单卡片上点「取消」",     // 触发方式（必填）
      "content": "标题 + 说明文案 + 底部两个按钮",      // 面板内容（必填）
      "close": "点「再想想」、点遮罩、按返回键",         // 关闭方式（必填）
      "form": "居中模态弹窗，宽 280，圆角 12，遮罩 45% 黑", // 展现形式（必填）
      "anim": "淡入 180ms + 缩放 0.94→1；关闭反向 140ms" // 动画效果（必填）
    }
  ]
}
```

**六个字段一个都不能少。** `form` 写清形态（居中弹窗 / 底部抽屉 / 侧滑面板 / 气泡 / 全屏页）、
尺寸、圆角、遮罩。`anim` 写清时长和缓动，没动画就写「无动画，直接显示」。

**每个菜单都要有一条 `interactions`。** 纯展示页也要写——首页没有弹窗，但有点击搜索框弹出的
搜索历史层、点校区名弹出的切换浮层，这些不写，研发就只能自己拍脑袋决定动画时长和关闭方式。
一个菜单一条都没有时，`validate.mjs` 会报警告并列名。

### 2.6 exceptions 章节（页面级）

页面级异常是一个独立章节，**只放跨功能点的通用异常**，渲染在页面说明的最后。

```jsonc
{
  "type": "exceptions",
  "title": "页面级异常",
  "note": "影响整页的通用异常（断网、无权限、版本过低等）。功能点自身的异常写在该功能点卡片的「异常场景」里。",
  "rows": [
    {
      "scene": "网络断开",
      "behavior": "顶部出现离线提示条，列表展示本地缓存数据，所有操作按钮置灰",
      "message": "「网络已断开，请检查网络后重试」"
    }
  ]
}
```

三个字段的含义：

- `scene`：什么条件下会出错，括号里补充具体触发原因
- `behavior`：系统怎么反应（关不关弹窗、按钮变灰还是隐藏、要不要回滚）
- `message`：给用户看的**原文**，用「」包住

`note` 可选，渲染成标题下的一行浅灰说明。页面级章节建议写上，避免研发以为这里漏了功能点的异常。

**分工口径**：拿不准某条异常该放哪一级，就问一句——**换掉这个功能点，这条异常还会存在吗？**
会 → 页面级；不会 → 挂到那个功能点下面。

**数量**：每个菜单页面级 + 功能点级合计至少 3 条，页面级本身不能为 0（否则断网、无权限没地方放）。
`validate.mjs` 会查这两条。

## 3. 字段表的四种形态与锁定列

`fields.table` 决定表头与哪些格子可以改。

| table 值 | 列 | 🔒 锁死 | ✏ 可改 |
|---|---|---|---|
| `list` | 元素 / 类型 / 展示逻辑说明 / 备注 | 元素、类型 | 展示逻辑说明、备注 |
| `form-add` | 元素 / 类型 / 必填 / 校验规则 / 默认值 / 备注 | 元素、类型、必填、校验规则、默认值 | **只有备注** |
| `form-edit` | 同上 | 元素、类型 | 必填、校验规则、默认值、备注 |
| `detail` | 分组 / 字段名 / 展示逻辑说明 / 备注 | 分组、字段名 | 展示逻辑说明、备注 |

**为什么这么锁**：锁死的是跟左侧原型焊在一起的客观事实（这个字段叫什么、什么类型）。
你把字段名改了，左边根本没这个字段，说明就成了假需求。开放出来的都是本来就该由人补的口径。

## 4. 编号规则

编号是「功能点」的编号，**不是需求条目的序号**。

1. 一个功能点在原型里**只标一次**。同一个功能点下有 4 个分类图标，只给第一个挂 `data-fp`，
   不要 4 个都挂——那样满屏气泡，没法看。
2. 编号挂在**独立按钮、输入框、区块、列表项**上。不要挂在：
   - `<tr>` 上（浏览器忽略 `tr` 的定位，气泡会飞掉）
   - 过窄的内联 `<span>` 上（气泡会溢出压住相邻文字）
   - **全宽容器上**（`.cart-bar`、`.me-head`、`.otabs`、`.navbar` 这类横跨整屏的元素）
3. 编号必须连续且从 1 开始（同一菜单内）。跳号会让研发以为是漏了。
4. 没有交互的元素不要挂编号。挂上去等于承诺「这里有一条需求」，实际却没有。

### 为什么不能挂在全宽容器上

气泡是绝对定位的小圆标，默认压在元素的**右上角**。挂在贴边容器上有两个后果：

- 容器宽到屏幕边缘，气泡向外溢出 → 被 `overflow:hidden` 切掉一半
- 容器内部右侧正好有内容（金额、箭头、状态文字）→ 气泡直接盖住它

正确做法是挂到容器内**左侧还有余量的具体控件**上：

| 错误挂法 | 正确挂法 |
|---|---|
| `.cart-bar`（底部结算条） | `.cart-bar .go`（「去结算」按钮） |
| `.citem`（购物车整行） | `.citem .stepper`（数量步进器） |
| `.me-row`（个人中心列表行） | `.me-list`（整组列表，有多行缓冲） |
| `.me-card .it`（数据卡里的单个格子） | `.me-card`（整张卡） |
| `.otabs` 里第一个 tab | 保持挂 tab，但要给 `.otabs` 留 `padding-top` |

### 自动防裁切 + 手动兜底

引擎在渲染后会自动检测每个气泡到容器四边的距离：

- 右侧放不下 → 翻到元素**左侧**
- 上方放不下 → 翻到元素**下方**
- 两侧都不够 → 收进元素**内侧**（半透明，悬停变实）
- **被某个 `overflow:hidden` 祖先裁切** → 收进元素**内侧**

最后一条要特别注意：移动端卡片常写 `border-radius:10px; overflow:hidden` 做圆角，
这个 `overflow:hidden` 会把子元素里的气泡裁掉，表现为"只剩一个缺角的小块"。
**如果卡片内部没有背景图或独立背景色，这个 `overflow:hidden` 是多余的，直接删掉。**
引擎的内侧兜底只是补救，内侧定位会压住内容。

自动判定覆盖不到的特殊情况，用 `data-fp-side` 手动指定：

```html
<div class="me-head" data-fp="14" data-fp-side="in">   <!-- 强制放在内侧 -->
<div class="xxx" data-fp="15" data-fp-side="tl">       <!-- 左上角外侧 -->
<div class="xxx" data-fp="16" data-fp-side="bl">       <!-- 左下角外侧 -->
<div class="xxx" data-fp="17" data-fp-side="br">       <!-- 右下角外侧 -->
```

只要写了 `data-fp-side`，引擎就不再自动调整这个气泡。

**如果某个元素本身需要绝对定位，就不要给它挂 `data-fp`**，改挂到它的父容器上，
否则 `position:relative` 会被引擎覆盖掉。

## 5. 编辑态与锁定

- 点顶栏「编辑需求说明」进入编辑态，可改格子变成黄底虚线框，点进去直接改。
- 每次输入写回内存中的 `DATA`，320ms 防抖后存 `localStorage`（key = `pageprd:<系统名>:<平台>`）。
- 顶栏出现黄条提示「本机有未合并的修改」时，说明浏览器里有改动还没回到文件。
- **改完必须点「导出 HTML」**，把导出的文件交给 AI 合并。只存在浏览器里的改动等于没做。
- 退出编辑态：点「退出编辑」或按 `Esc`。导出快捷键 `Ctrl/Cmd + S`。

## 6. 导出与合并协议

```
浏览器改说明 → 导出 HTML → node scripts/merge-spec.mjs <导出> <目标> → 数据回写
```

`merge-spec.mjs` 只做一件事：把导出文件里 `#prd-data` 的 JSON 替换到目标文件，
**原型区 HTML 一个字不动**。同时会：

- 校验 `system` 与 `platform` 是否一致（防止 Web 端和移动端互相合并）
- 打印变更摘要（JSON 路径 + 旧值 + 新值），方便人工核对
- 自动备份 `<目标>.bak.html`
- `--dry-run` 只比对不写入

导出 Markdown 走另一条路：`node scripts/export-md.mjs <index.html>`，
只读不写，生成 `原型文件` 同目录的快照副本。

## 7. 生成时必须守的规矩

1. **原型动了，说明必须跟着动。** 只加按钮不补说明 = 没交付。
2. **一个功能点一条说明，一条说明一个编号。** 不要出现"其他"、"杂项"这种功能点名称。
3. **业务规则写成可判定的句子。** 写"手机号重复时阻止提交"，不写"注意手机号校验"。
4. **不擅自加原型里没有的功能。** 说明里写的每个元素，左边必须找得到。
5. **不把口径留空。** 权限表的数据权限列、状态流转、金额公式，必须给具体值；
   确实待定的写「待确认：<具体问题>」，让研发知道这里要问谁。
6. **每个菜单必须有布局说明。** 讲清页面从上到下分了哪几块、每块里有什么、空状态长什么样、
   怎么刷新。`validate.mjs` 会把缺布局说明的菜单判为**错误**。
7. **每个菜单都要有一条交互说明。** 不是"画了面板才写"——纯展示页也要写清「点哪里会弹出什么、
   弹出来后怎么关」。一个菜单一条都没有，等于这一页的交互没人设计过。原型里有弹窗 / 抽屉 / 浮层 /
   下拉面板的，必须有对应的 `interactions` 条目，六个字段齐全。研发最常问的三个问题就是：
   怎么弹出来的、怎么关掉、有没有动画。
8. **业务规则要带前置条件和流程。** 条件分支超过 2 个、涉及外部系统（支付、短信、OCR）的功能点，
   必须有 `flow`；依赖登录态、权限、基础数据的功能点，必须有 `precondition`。
9. **每个菜单都要有异常场景。** 接口调用、权限校验、文件上传、支付、定位、相机，每一类至少一条，
   写清系统表现和提示原文。确实是纯静态页面，也要写"资源加载失败"这类降级，不要留空。
10. **示例数据要覆盖全部菜单。** 演示文件是给人验收的，默认打开第一个菜单。新能力只写在第二个
   菜单里，验收的人第一眼就看不见，会直接判定"没做"。`validate.mjs` 会对"部分页面有、部分页面空"
   报**警告**并列出页面名。

## 8. 常见错误速查

| 现象 | 原因 | 修法 |
|---|---|---|
| 右侧空白，什么都不显示 | `PRD_DATA` JSON 语法错误 | 用 `validate.mjs` 定位 |
| 切菜单右边不变 | `data-menu-btn` 的值和 `menus[].id` 不一致 | 对齐 id |
| 气泡点了没反应 | `data-fp` 的值在说明里不存在 | 补功能点或改编号 |
| 气泡位置乱飞 | 挂在了 `<tr>` 或绝对定位元素上 | 移到 `<td>` 或父容器 |
| 编辑后刷新丢失 | 只改了 DOM 没写回 `DATA` | 用模板自带的编辑态，别手动改 |
| 合并后说明没变 | 忘了先点「导出 HTML」 | 重新导出再合并 |

## 9. 图标与图片资源

原型不是示意图，是能直接交给研发切的 UI。所以**不用 emoji、不用几何字符（◈◇◆▣⌂▢◔）当图标**。

### 9.1 图标：内联 SVG symbol

模板里已经内置图标库，放在 `<body>` 开头的 `<svg class="svg-sprite">` 里，全部是
`viewBox="0 0 24 24"`、`stroke-width:1.8`、圆角端点的线性图标。

用的时候：

```html
<svg class="ic"><use href="#i-home"/></svg>
```

`.ic` 类控制尺寸和颜色：

```css
.ic{width:1em;height:1em;fill:none;stroke:currentColor;stroke-width:1.8;
    stroke-linecap:round;stroke-linejoin:round}
```

- 改大小 → 调父元素的 `font-size`（因为 `.ic` 是 `1em`），或直接写 `style="font-size:20px"`
- 改颜色 → 调父元素的 `color`（`stroke:currentColor` 自动跟随）
- 实心图标 → 加 `class="ic fill"`

**移动端已有图标**：home、order、cart、user、search、right、left、more、plus、minus、
star、clock、pin、burger、noodle、salad、drink、shop、ticket、invoice、service、settings、check、close、signal、battery

**Web 端已有图标**：lead、users、trend、shield、inbox、clock、funnel、search、plus、check、close、right

**要加新图标**：在 sprite 里按同样的风格补一个 `<symbol>`，`id` 前缀 `i-`。
不要引入图标字体或外部图标库——单文件交付会失效。

### 9.2 图片：容器定尺寸，图片可替换

banner、店铺 logo、商品图、头像这类"应该是照片"的位置，结构上必须是**可替换的图片位**。

**当前模板的做法**（无外部依赖，矢量渲染）：

```html
<!-- 带品牌底色的图标位 -->
<div class="ph" style="background:linear-gradient(135deg,#DBEAFE,#BFDBFE);color:#1D4ED8">
  <svg class="ic" style="font-size:28px"><use href="#i-shop"/></svg>
</div>
```

**换成真实图片时**，只改标签，尺寸和圆角都不动：

```html
<img class="ph" src="./assets/shop-01.jpg" alt="青禾小馆">
```

前提是容器的尺寸、圆角、`overflow` 已经定义好：

```css
.m-shop .ph{width:62px;height:62px;border-radius:9px;object-fit:cover;flex:0 0 auto}
```

**关键约定**：

| 位置 | 尺寸 | 圆角 | object-fit |
|---|---|---|---|
| 店铺 logo `.m-shop .ph` | 62×62 | 9px | cover |
| 商品图 `.dish .ph` | 64×64 | 9px | cover |
| 订单商品图 `.oitems .ph` | 52×52 | 7px | cover |
| 购物车图 `.citem .ph` | 56×56 | 8px | cover |
| 运营 banner `.m-banner` | 通栏 112 高 | 10px | cover |
| 用户头像 `.me-head .av` | 54×54 | 50% | cover |

### 9.3 为什么不用 base64 内嵌照片

1. **文件会膨胀**：一张 800×400 的 JPEG 转 base64 后约 100–150KB，几张图就能让 HTML 翻倍。
2. **不是生产做法**：正式环境的图片一定走 CDN 或本地静态资源，base64 反而增加首屏体积、无法缓存。
3. **不可维护**：研发拿到文件后无法替换图片，只能重新生成整个 HTML。

所以原型阶段的正确姿势是：**结构上留好图片位，视觉上用矢量图标撑住**。
需要看照片效果时，把 `src` 指向真实图片文件即可，不需要改任何样式。

### 9.4 banner 这类运营位

运营位的内容（文案、图片、跳转）在正式环境由后台配置，前端不该写死。
原型里用「渐变底 + 文案 + 矢量插画」表达，研发一看就知道这是个图片位：

```html
<div class="m-banner">
  <div class="txt"><b>午餐补贴上线</b><span>工作日 11:00-13:00 满 20 减 5</span></div>
  <svg class="bn-art" viewBox="0 0 168 168" aria-hidden="true">…</svg>
</div>
```

替换为真实图片时，整块换成：

```html
<img class="m-banner" src="./assets/banner-01.jpg" alt="午餐补贴上线">
```

（前提是 `.m-banner` 上已经定义了 `height` 和 `border-radius`。）
